# Windows Pi command jobs

This source adapter replaces direct-process-only Stop for approved Pi shell jobs. It reuses the product's independently authored `OwnedProcess` and `process_worker.py`; it adds no dependency, native binary, copied supplier source or second agent loop. The public Pi session owner and durable job registry remain unchanged. Installed Windows acceptance, physical platforms and the full accepted migration remain open.

The Node producer starts the product Python interpreter with isolated flags and one private stdin/stdout protocol. The Python supervisor retains an unnamed kill-on-close Windows Job. The existing worker joins that Job before starting the command workload, then closes its inherited Job handle. The workload sends a private readiness marker before receiving command text. Only after that marker does the supervisor report the range ready and release the approved command. Missing containment or readiness has no direct shell fallback.

Commands use `%SystemRoot%/System32/cmd.exe /d /s /c` and preserve the original command's quoting/operators. `/d` disables CMD AutoRun. Requests are bounded, strict versioned JSON; the literal complete CMD invocation is refused above 8191 UTF-16 units before releasing work. CMD environment expansion and batch processing retain their own native limits; this is not a general quoting or shell-language translation. See [Microsoft CMD](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/cmd) and [the native command-line limit](https://learn.microsoft.com/en-US/troubleshoot/windows-client/shell-experience/command-line-string-limitation).

The supervisor encodes separate stdout/stderr bytes as bounded base64 frames. Printed JSON is ordinary command output and cannot forge control receipts. The Node decoder preserves partial UTF-8 characters, rejects foreign/malformed/oversized/noncanonical frames, and accepts a confirmed receipt only after a clean helper exit with no trailing partial frame. Per-frame bounds permit a transport chunk containing many valid frames. Storage failure or missing/malformed settlement is unknown, without automatic replay. Helper stderr is diagnostic rather than an untrusted command receipt.

Stop or stdin EOF terminates the exact owned Job. Host crash closes the private lease; supervisor crash closes the final Job handle. The supervisor observes the Job's active-process count after its worker exits, so a detached surviving descendant retains ownership and capacity until natural drain or Stop. A successful stop receipt requires observed drain; a three-second drain failure reports unknown. Node's four-second helper watchdog closes a stuck owner's Job but cannot substitute for a missing receipt. The existing registry's five-second unknown boundary and restart-without-replay behavior remain in force. No saved or discovered PID is adopted for product cancellation.

Windows Job membership covers ordinary `CreateProcess` descendants, including detached processes. It does not sandbox file/network effects or undo earlier actions. External launch mechanisms such as WMI/service requests can create processes outside membership. Product containment cannot certify their exit. See [Microsoft Job objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects). Unix shell behavior remains the existing exact process-group TERM/KILL adapter; this new Windows lease does not qualify Unix Host-crash descendant cleanup.
