# Managed MCP dispatch and failed acknowledgments

The accepted Harness migration requires unknown action outcomes to survive reconnect without replay. Pi 1.1.0's SDK retries any MCP request once after `McpSessionExpiredError`, assuming an HTTP 404 means the server did not execute it. An independently authored actual HTTP/SDK-owner fixture disproved that assumption for a server that applied a mutation before returning 404: one logical tool call changed the fixture twice. This is a reproduced integration failure, not a claim that compliant MCP servers normally behave this way.

Augmentor now supplies `managedMcpTransport` through the supported `createMcpExtension({createTransport})` hook. The pinned public `@earendil-works/pi-mcp` **1.1.0** transport package is declared directly; it was already present in the production lock graph. The SDK retains its existing AgentSession, MCP clients, discovery, tool pipeline, nested calls, OAuth credentials and lifecycle. No separate agent loop or SDK-private import is added.

## Dispatch boundary

HTTP JSON-RPC `tools/call` requests receive manual redirect handling. A failed HTTP response after dispatch becomes a public `McpHttpError` with its real status and an explicit unknown outcome; it cannot become the SDK's automatically retried session-expiry error. Error bodies remain private original evidence rather than being inserted into model context. A dropped acknowledgment remains a failed, unknown dispatch through the existing SDK and action ledger.

Before SDK result normalization, the managed owner appends **`augmentor-mcp-transport/1`** native custom entries containing the configured server name, transport request ID, actual dispatched method/parameters, status/content type and retained error body. Transport request headers, their bearer credentials and the configured server URL are not copied into that entry. Dispatched parameters and returned bodies retain their original private data. It is independent of diagnostic capture and does not insert a model message or memory source. Existing native original search/read/export can inspect it. The agent’s existing `tool_result_excerpt` also admits [retained HTTP bodies](#agent-recovery-of-retained-http-bodies) through explicit branch-scoped reads. The transport request ID is not claimed to be a canonical agent tool-call ID; complete causal provenance remains separate work.

Body retention captures up to **1 MiB**, with a **500 ms** body-read deadline, exact retained bytes as base64, a retained-prefix SHA-256 and decoded text. Complete, partial and unavailable coverage plus reasons distinguish a full body from truncation, failed reads or a stalled stream. A failed native save adds an explicit evidence-gap message. Successful JSON-RPC tool results continue through the existing SDK/tool-original path; this entry covers failed HTTP acknowledgments, not exact transport bytes for every MCP interaction. These native entries share Pi session privacy, retention and deletion semantics; clearing optional diagnostics leaves them intact.

On a 401 or a 403 `insufficient_scope` challenge, the SDK-supplied auth provider may refresh credentials or record its authorization challenge. The failed tool call is still rejected; refreshed credentials do not authorize resending that call. Pre-dispatch token refresh remains owned by the SDK. A typed `McpOAuthAuthorizationRequiredError` is delivered after [sibling calls and controls settle](#authorization-errors-and-parallel-receipts), preserving the SDK's sign-in handling for a still-pending caller. Other refresh/challenge exceptions become a sanitized unknown HTTP outcome; the provider's raw message is not inserted into model output. HTTP metadata/resource requests retain the normal SDK retry/auth behavior because they do not dispatch tools.

After a guarded HTTP tool failure, the old connection closes once its concurrent tool requests and outgoing cancellation notifications settle. Public response listeners retain pending IDs through asynchronous SSE receipts; SDK cancellation removes timed-out/cancelled IDs. An explicit client/transport close releases local drain waiters. A later explicit operation can initialize a new SDK connection. The guard does not patch private SDK/client fields or change an active conversation's model, tool permissions, execution mode, approved settings or owner release.

Stdio retains the public SDK transport and platform home/cwd/shell behavior. The selected MIT [configuration resolver](../packages/runtime/vendor/pi/SOURCE.md#configuration-value-resolver) preserves environment references, literal escapes and trusted command values. Its only source edit uses the public SDK shell export. Missing configuration values produce a sanitized error. Managed configuration remains `agent/mcp.json`; project files and other Pi profiles remain excluded. Server logs remain opt-in and private.

## Authorization errors and parallel receipts

An isolated actual Pi SDK session in explicitly selected **parallel** mode reproduced a lost receipt: one tool applied a synthetic mutation and returned a scope challenge; the SDK's typed sign-in handling closed the client before another tool's delayed SSE result arrived. `tests/pi-mcp-parallel.test.mjs` now exercises the same public SDK, managed MCP factories and real HTTP/provider wire with one or two distinct failing calls plus a successful sibling. Deferred typed errors retain the sibling receipt, the SDK's `requires sign-in` result and one dispatch per original call. Native's existing **sequential** mode is unchanged. The actual private-owner fixture separately qualifies a scope failure and a separately requested sequential read, with an unknown mutation outcome and no automatic replay.

The transport tracks public request IDs for both tools and metadata/resources, plus response/cancellation events. Calls already known to have failed authorization do not wait on one another; they wait on other already-admitted requests and cancellation POSTs. This protects delayed resource receipts as well as tool receipts. Ordinary cancellation sends settle before automatic reset or deferred sign-in handling; their arrival is not proof the remote operation stopped. Explicit close clears the local wait boundary, and ordinary SDK request deadlines are preserved.

Public-client fixtures cover sibling cancellation, failed-call cancellation, sibling timeout, the failed call's own timeout, both calls cancelled and explicit client close. A cancelled/timed-out failed caller receives its actual SDK abort/timeout result; an ignored deferred error is not delivered retroactively. [Independent native authorization observations](#recorded-authorization-requirements) retain the requirement even when the SDK caller no longer receives it. The HTTP original survives independently, and a surviving sibling result is retained without action replay. Exact auth-provider exception payloads are not an additional captured boundary; the guard saves tool HTTP originals and sanitizes callback exceptions.

The same public factory now protects admitted requests before handing HTTP authorization failures from metadata/resources or the server-to-client GET stream back to the SDK. It permits the SDK's ordinary metadata credential handling, while resetting the challenged connection after admitted requests settle. SDK refresh requests to other endpoints remain unchanged. HTTP close/control notifications do not wait on their own cancellation POST. New tool calls during a known failed acknowledgment or auth drain are rejected **before dispatch**, with no queue or automatic resend; existing requests, credentials refresh and cancellation continue to settle. This refusal is not a new canonical action-ledger linkage.

Actual public SDK fixtures reproduce two additional lost-receipt baselines: a resource sign-in error discarded a pending tool result, and a tool sign-in error discarded a pending resource result. Both receipts now survive. The baseline GET challenge retained its healthy tool receipt but lacked a recorded sign-in requirement; that evidence is distinct from a reproduced GET receipt loss. The timeout case staggers an admitted read within unchanged one-second SDK request deadlines so the failed write times out before the read returns. Final receipts, timeout identity, one write dispatch and saved/cold-restored sign-in observations pass. Native remains sequential. Pre-dispatch token-provider exceptions, arbitrary stream/drop errors, live OAuth UI/refresh/rotated-credential persistence and representative services remain acceptance work; these fixtures do not qualify the complete OAuth lifecycle.

## Recorded authorization requirements

Private **`augmentor-mcp-authorization/1`** native custom entries record server name, optional public transport request ID, HTTP 401/403, a tool/request/GET/control response boundary, observation time and one of **challenge-observed**, **sign-in-required**, **refresh-failed** or **challenge-handled**. Admission requires JSON-RPC POST or GET at the configured MCP URL; a non-RPC refresh response even at that same URL is not MCP response evidence. Entries contain no body, headers, URL, challenge scope or token. Challenge-handled means the callback completed; it does not prove a retry, sign-in success, the scope of other operations or current credential health. The observations are independent of optional diagnostic capture and excluded from SDK model context. They are observed before the typed error waits on remaining requests.

Loaded `session.mcpInfo` exposes the latest validated observation per currently registered server on `SessionManager.getBranch()`. Strict recovery strips unknown fields and rejects malformed/oversized metadata. Native retains its normal generic sign-in/refresh notices and `integration/mcp-authorization` metadata. Cold SDK restoration preserves these original entries without inference or action replay. Existing cold catalog reads still do not load a conversation or connect an MCP server. Removed server registrations do not become a live connection catalog.

Native append failure is an explicit gap: loaded inspection distinguishes an **unsaved** observation and `native-append-failed`, and the owner emits a generic evidence warning. A public-SDK append fault injection verifies surviving receipts, no provider-message leak and no invented cold recovery. Ordinary saved observations follow SDK native-entry storage; blank sessions retain the SDK's deferred file-creation policy until a conversation exists. Diagnostic clearing does not delete these native entries. Full causal native/transport/agent IDs and live account/installed acceptance remain open.

## Agent recovery of retained HTTP bodies

Omitting `entryId` from `tool_result_excerpt` lists the latest twenty eligible originals on the current Pi branch. HTTP entries expose the native entry ID, server, method, transport request ID, HTTP status/content type, complete/partial/unavailable coverage, retained bytes/prefix SHA and any retention reason. Listing excludes body text, dispatched parameters and base64. No canonical agent `toolCallId` is invented; the boundary is labelled **`http-tool-failure-before-sdk-error-normalization`**.

An explicit entry read returns at most **2,048 code points** of decoded retained body text using the existing offset or literal case-insensitive `find` interface. Character counts and `nextOffset` describe that retained prefix. **`responseBodyComplete: false`** and the coverage reason remain present after a partial read reaches its end. Unavailable bodies return an explicit gap; binary-like text remains withheld even through a one-character excerpt. Base64, parameters and headers are not added to agent excerpt responses. Returned text is historical untrusted evidence, not execution authority, proof of an action's completion or permission to resend it. Explicitly recovered text becomes an ordinary tool result in the conversation, subject to existing history and context-budget behavior.

Admission validates the bounded native body shape, canonical base64, retained byte count, prefix digest and exact UTF-8 decoding. Malformed/corrupt records and another custom entry type are not admitted. Only `SessionManager.getBranch()` is read; an abandoned future or another conversation cannot be retrieved. Reading does not mutate the original custom entry, repair/clear the unknown action outcome, contact an MCP server or start a second agent loop. A provider turn itself still follows the ordinary SDK session/resource lifecycle.

`tests/pi-tool-budget.test.mjs` covers complete Unicode/search/paging, metadata-only listing, partial/unavailable coverage, binary withholding, corruption/shape rejection, immutable originals and branch isolation. `tests/pi-mcp.test.mjs` drives the actual owner and synthetic provider after a failed mutation: a new explicit read reconnects, lists the HTTP metadata and calls the excerpt tool; the original body first appears in a provider request after that explicit read, with diagnostic capture off and the mutation count still one. These are synthetic source/package contracts; full causal IDs, long-history performance, live accounts/services and installed acceptance remain open.
