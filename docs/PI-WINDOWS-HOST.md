# Pi Host on Windows: source adapter candidate

The focused Windows command workflow at `26528e9b2e1155b50e8610d66989761944b1b393` exposed a genuine Host startup gap: Pi tried to bind its POSIX filesystem socket on Windows. It also exposed the registry's POSIX mode assertion and the absence of kernel ACL protection in Node's private-record writes. [x64 evidence](https://github.com/ManoloRemiddi/augmentor-agent/actions/runs/38121498504/job/114416997189): 26 Node cases/10 passes/16 failures/no skips. The eight real shell-helper tests passed, but no Host command case reached execution. This evidence supersedes any assumption that those helper tests proved the full Windows owner path.

The correction uses the existing `ThreadingPipeServer`/`PipeSocket` machinery: current-user/SYSTEM ACLs, remote rejection, first-instance exclusion and kernel peer-token verification. A small independently authored Python relay owns that listener. Bounded versioned stdio frames map each connection to a distinct opaque ID; client bytes are base64 data, never relay commands. The Node-facing Duplex objects preserve the existing newline RPC and BrowserBroker identity. There is no TCP port, reusable PID, supplier-private source, SDK patch, separate agent loop or UI change. Endpoint ownership is acquired before opening session journals; Unix continues to use its existing socket.

The relay admits at most 32 clients. Each client has a bounded write queue; slow clients cannot block the parent's input/EOF lease. Fragmented data is at most 64 KiB per frame, with independent frame/input/output bounds and per-client Node buffering. Malformed relay evidence closes the transport. Parent stdin EOF or explicit shutdown stops the listener and closes every owned client pipe. Relay failure stops the Host rather than preserving an owner with no operator transport. The existing client relay still verifies the server's kernel identity before application bytes. General action effects and trusted extension code remain outside transport containment.

Windows Pi private directories and atomic records now use the existing isolated Python ACL/reparse/single-link validation and durable replacement operations. Metadata reads validate the opened private object before returning JSON. Unknown identities, broader existing ACLs, junctions and unsuitable files are refused; the adapter does not silently tighten or adopt other state. Newly written records receive protected user/SYSTEM ACLs, rather than treating Windows `chmod` bits as privacy evidence. Fixtures use the same production directory/record adapter, and the registry verifies a real private descriptor on Windows while retaining its POSIX mode check elsewhere.

This is an unqualified source correction until the new exact-head Windows Host/SDK workflow passes. The preceding kernel-helper, prepared Linux source/Python and ordinary stage-21 results belong to the preceding implementation and do not prove this new relay/record integration. The complete assembled Windows workflow and physical/installed acceptance remain independent required gates. DSH, installed selections, canonical dirty main, approved UI and explicit model/speech/GPU placement are preserved. The full Harness goal remains active.
