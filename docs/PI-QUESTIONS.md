# Original question controls on Pi

The original MIT DSH QuestionComposer now binds its countdown, **Take time**, editing and focus controls to the same Pi Host that owns the question. Supplier components, CSS and licences are unchanged. This is an Augmentor UI/Host binding through Pi 1.1.0's supported ExtensionUIContext, not a second question service or conversation loop.

The Host supplies a revisioned `wait` snapshot on `question/requested`: phase, remaining foreground budget and a deadline when counting. The initial budget is the smaller of the extension's requested timeout and the managed default (120 seconds unless explicitly configured). `interaction.wait` accepts only the exact pending question, session and operator client. Take time changes the question to waiting; the first edit changes it to editing. Both remove the foreground deadline until answer, cancellation or disconnection. Extension AbortSignal, parent/child Stop and owner settlement continue to cancel the request. This foreground-pause policy is implemented by the supported custom UI adapter; it does not promise an unmodified wall-clock timeout while the operator pauses it.

Focus temporarily freezes the pristine budget. Each client has a separate 15-second lease, renewed every four seconds while the selected question remains focused and polling succeeds. Releasing one client cannot release another's focus. The last release or expired lease resumes the remaining budget. A browser crash cannot retain an indefinite focus hold. The Host checks continued UI availability at least once per second; after the last operator watch expires or the last native subscriber disconnects, unanswered questions settle without an answer. Read-only inspectors cannot pause, engage, focus or answer.

Approval requests retain their existing hard timeout and cannot use these pause controls. They do not silently acquire indefinite approval waiting. Late answers and wait controls fail after settlement. Question expiry resolves the actual SDK dialog with no answer; no later-answer channel or fabricated “work continued and you can still answer” state is exposed. No answer, model request or external action is retried by these controls.

The browser reads canonical phases and revisions, ticks only the displayed remaining count and never settles a question using its own timer. Older event/RPC snapshots cannot replace newer state. A stable original pending carrier avoids releasing focus during an ordinary timing update. Draft stores are scoped per conversation, so another conversation cannot prune or display an unfinished answer. Drafts survive component collapse/remount and switching within the current page; answer-draft persistence across a full page reload remains unimplemented. Pending Host questions do survive page reconnect within the running process; Host restart does not reconstruct or replay them.
