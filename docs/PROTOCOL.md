# Augmentor Pi client protocol v1

Transport: UTF-8 newline-delimited JSON over an owned, mode-0600 Unix socket. Maximum frame: 1 MiB. Slow event consumers are disconnected rather than accumulating unlimited server buffers. This is the app's transport contract; Pi SDK types remain inside the host.

Begin every connection with `{"id":"hello","method":"host.hello","params":{"protocol":"augmentor-pi/1"}}`. The matching response has `id` and `result`; errors have `id` and `error.message`. An incompatible version is rejected. Request IDs are ASCII letters/numbers/underscore/dot/hyphen, up to 128 characters.

Display messages use `method: session/event`, `payload.sessionId`, and `payload.event` containing a durable `seq`, display `type`, `data`, and when applicable a `turnId`. Display types include user/message, assistant/chunk, assistant/message, tool/call, tool/result, session/title, runtime/error, runtime/warning, runtime/notice and turn/start/end. Display events are a private recovery projection; Pi's session files own the conversation supplied to the agent.

`mcp/connection` is a transient session event with `payload: {sessionId, observation, retained}`. Its whitelisted `augmentor-mcp-connection/1` metadata has transport-instance identity/sequence and observed public lifecycle events; `retained` means native append acceptance under SDK persistence policy. Failed appends also produce a generic `runtime/warning`. Events contain no arbitrary supplier error/body/configuration data and are not model context or proof of current service health. See [the connection contract](MCP-TRANSPORT.md#observed-connection-lifecycle).

Pi `session.history` now uses the same derived byte-offset reader for loaded and cold sessions; `host.describe.capabilities.indexedDisplayHistory` advertises it. The response shape remains `{events: [{event}], hasMore}`. Continue backward with the first returned event's original sequence. Compaction is resolved against the full saved journal before the cursor: deltas represented by a later nonempty final answer cannot reappear on an older page. Interrupted/empty-final deltas and tool boundaries remain. Valid persisted indexes avoid whole-journal reads after restart; rebuilding a derivative streams the source. A single oversized event fails with its original preserved. Reading history never loads a Pi AgentSession, invokes the provider or changes native history. SDK resume/branch/edit/memory initialization retain their separate full-state lifecycle.

Pi `host.describe.capabilities.indexedNativeHistory` advertises private derived original-entry indexes. Native reads do not open/resume an AgentSession, infer, repair native files or accept client paths. Version-3 only; unsupported/corrupt complete records and records above 64 MiB fail with originals preserved; incomplete tails are reported. Metadata verifies header and returned entry boundary blocks, not all middle bytes/ancestors; excerpts verify each returned block against the indexed snapshot even with colliding file timestamps. Changed verified blocks rebuild derivatives; supplied hash guards refuse changed entries/ancestry. Whole-source streaming remains necessary for initial/stale rebuild. Scoped read-only inspection permits these two reads only for its selected conversation. See [native coverage](AUGMENTOR-HARNESS.md#indexed-native-entries-and-canonical-message-lineage).

Questions and approvals carry a unique `rpcId`. Subscription reattachment redelivers pending interactions; a resolution emits `interaction/resolved`. Default timeout is two minutes. Stop, timeout or losing the last subscribed UI resolves a pending action without permission to execute it. No connected UI means manual actions are denied. Completed interactions cannot be answered again.

The Python client never automatically retries prompts or tool actions. New admissions retain stable ID/fingerprint receipts in `<Pi state>/sessions/<id>.queue.json`; terminal receipts discard historical prompt text. Reusing an identity with different input is rejected; repeating it with the same input returns its receipt without execution. Older sessions retain their historical last-100-ID compatibility list. This provides local admission deduplication, not a transaction guarantee for external actions. Reconnect reconciles history and live frames by `seq`. Restart records interrupted work, marks any dispatched nonterminal receipt unknown and pauses waiting inputs; it never replays them. A prior external action may have completed before a crash, so a user must inspect that outcome. **Keep interrupted** explicitly acknowledges the receipt and leaves waiting work paused. An explicit idle Send resumes older waiting inputs before the new prompt; Continue resumes only the existing queue.

`session/queue` is a complete replacement with `payload.sessionId`, monotonically persisted `revision`, `paused`, `activeTurnId` and `items`. Each item carries `id`, `rpcId`, text message, placement, state label and `canRemove`, `canSteer`, `canResolve`. Subscription returns the current baseline without execution; the HTTP inspector receives it in the subscription result. Delivered `user/message.data.source.rpcId` identifies its admission receipt. Unknown action receipts remain visible even when user-message delivery was confirmed. Waiting/visible queue state is bounded to 100 rows and 512 KiB; dispatched and unresolved inputs cannot be removed or automatically retried. The current candidate advertises `queue: true`, `steering: true`. Pi's transient string queue does not own product input persistence.

One identified correction may await delivery within the active SDK session. Promotion persists its original ID, text fingerprint and observed turn before using the public Agent owned by AgentSession. Only the obsolete provider request is aborted; dispatched tools retain their SDK run signal and settle before delivery. Obsolete proposals cannot dispatch afterward. The correction and its answer remain in the original host turn; normal FIFO follow-ups begin after that SDK prompt settles. Repeated promotion returns its receipt without another message. Stale turns, Stop and the settling phase reject new promotion.

`host.describe.steering` declares `input: sdk-public-input-and-approved-resources`, `sdkInputTransforms: true`, `inFlightTools: settle`, `continuation: same-AgentSession` and `identity: owned-message-reference`. Steering runs the public SDK input-handler chain with source `rpc` and mode `steer`, then expands only the session's approved skills and loaded prompt templates. Images supplied by input transforms are preserved. Registered extension commands are rejected before admission/promotion; steering does not execute commands. The selected MIT Pi template utility preserves the pinned SDK's argument/substitution semantics. No resource discovery or private SDK access is added. Native message object ownership binds delivery to its exact request ID; matching text cannot establish identity.

Ordinary and queued inputs now use the same session's `AgentSession.prompt` with `source: rpc` and `expandPromptTemplates: true`. Approved input handlers run once; transformed text/images and approved skill/template expansion reach the normal SDK provider path. Registered commands fail before durable admission and are checked again before dispatch. `host.describe.promptInput` discloses that expansion, command restriction, disposition callback and Stop boundary. The exported Pi 1.1.0 `PromptOptions.preflightResult` reports `started`, `queued` or `handled`; upstream describes it as an internal hook for RPC dispatch observation. This host uses that typed SDK RPC callback, not private imports or fields. Its behavior is pinned and exercised by actual SDK tests; upgrades must requalify it. [Harness shared picker/editor](AUGMENTOR-HARNESS.md#shared-prompt-library-and-editor) now has source/staged qualification; full command/resource composition remains a separate gate; isolated Pi draft improvement is qualified in the later contract below.

Harness library/editor requests use the same authenticated operator RPC and shared service without requiring an active session or submitting model input. Save/Delete use service-owned IDs/revisions. The picker inserts saved text into an editable draft before ordinary admission, reading one clipboard snapshot only on explicit selection. Pending or stale-context reads cannot send or replace a new draft. Opening/saving the editor does not expand clipboard content. Conflicts preserve edited text; reconnect reads the latest library without replaying a write.

An ordinary input consumed by an extension completes its receipt once, records `execution/input` and `input-handled`, and emits a durable status notice with original `submittedContent` and originating `source.sessionId`/`rpcId`. It adds no fabricated human/model message or conversational-memory item. Native/Browser clear only the matching own-origin optimistic submission. Stop during ordinary asynchronous input preparation blocks provider dispatch while the trusted handler settles; it does not promise to terminate arbitrary handler effects. The single SDK owner remains busy until settlement. Stop, preparation failure or crash leaves uncertain processing unknown and paused, even if the SDK subsequently appends native input. Explicit acknowledgment never retries the handler or confirms its effects.

Durable admission and receipt promotion are serialized. Asynchronous input preparation runs outside the host state lock; status reads, Stop and interaction replies can still proceed. The obsolete provider is cancelled immediately and the composed public finish hook holds the safe SDK boundary until preparation and its durable callback settle. A handler returning `handled` completes the correction receipt without claiming model delivery, returns `handled: true`, and records an `input-handled` execution outcome and durable status notice. No fabricated user message or assistant answer is added. Duplicate requests/promotions do not repeat the handler. Failure records a runtime error and leaves the correction outcome unconfirmed.

`user/message.data.content` remains the actual SDK content used for native history/branch matching. When preparation changes it, optional `data.submittedContent` preserves the original accepted user text, with the same `source.rpcId`. Chat, copy/edit controls and Pi conversational memory prefer that original submission; Context displays the effective prepared request. Handled-input status notices retain the original submission but are not conversational-memory items. Both original and prepared text are ordinary private history, separately from opt-in diagnostic payload capture; see [data disclosure](DATA-AND-SUPPORT.md).

Stop clears the SDK queue synchronously and returns only corrections still present in its public queue preview to paused product waiting work. It also releases a pending input-preparation boundary, returning `interruptedPreparation: true` when applicable. Processing handlers may already have effects; an interrupted preparation or selected message with unconfirmed delivery stays unknown rather than being guessed back into waiting. A late handler result cannot enqueue a correction after Stop. Crash recovery marks both the active and promoted nonterminal receipts unknown, pauses the queue and never retries them. Finishing the root receipt atomically settles delivered steering receipts; undelivered ones remain unknown. The per-turn action ledger survives steering, guarding repeated changes and changes after uncertain actions while allowing reads. An ordinary later human turn retains the existing permission contract. See [queue and steering qualification](QUEUE-AND-STEERING.md#pi-approved-steering-input--october-10-source-candidate).

The native policy values are `read-only`, `workspace-write` (UI label “Ask before actions”), and `danger-full-access`. The middle mode asks for all state-changing/unknown tools; its historical identifier does not imply an OS filesystem sandbox. Policies are snapshotted at chat creation.

The published distribution includes `dist/protocol/schema.json`, request/event fixtures in `dist/protocol/fixtures/`, and the TypeScript declarations in `dist/protocol/src/`. The schema validates the request envelope; method-specific validation is implemented in the host and covered by contract tests.

Literal Bash queries for the clock (`date` with display flags/format), working directory (`pwd`), identity (`whoami`, `id`), kernel (`uname`), uptime, memory (`free`) and disk usage (`df`) run without approval in both read-only and ask-before-actions chats. Only explicitly recognised arguments qualify. Shell pipelines, redirections, substitutions, clock-setting arguments and other commands keep the normal policy. This classification also applies when existing chats resume.

Message branching uses Pi SessionManager on a separately opened source. The child owns a separate Pi session file and display journal, inherits the source working directory, model selection and tool policy, and records its source and message sequence in metadata. Earlier tool calls/results remain context without executing again. Branching itself submits no prompt. Edited resubmission first creates an edit branch, attaches/subscribes to it, then sends the revised text through the usual prompt path. Original conversations remain unchanged. Display sequences are local to each conversation; clients must keep the conversation ID with an edit target.

An initial input's edit display cutoff precedes its `turn/start`. A steered input shares that host turn with earlier human/assistant/tool messages; its edit cutoff precedes the selected `user/message`, preserving that earlier prefix to match the native Pi parent. New Pi human display records include `data.source.sessionId`, the originating conversation, alongside any `rpcId`. Cloned display records preserve that origin; absent legacy origins are filled with the source conversation when cloning, without modifying the source. Inherited IDs are historical evidence, not delivery of a child's prompt. Harness/Browser queue reconciliation and Native/Browser pending-submission confirmation accept a recorded origin only when it matches the viewed conversation. Legacy messages with no origin retain their earlier confirmation behavior.

Harness Chat exposes Branch on persisted text replies without tool proposals, and Edit only on the latest persisted human input. Actions are unavailable while running or submitting. Edit preparation and Cancel perform no RPC/inference; Send edit creates a child at the exact native parent and admits the captured edited text through the durable queue. Conversation/epoch guards protect newer drafts from late branch completion. A failed branch preparation retains its child ID for an explicit retry; successful completion releases it so a later intentional Branch creates a fresh child. Queue admission uncertainty belongs to the queue receipt and ends the editor without automatic resubmission. The selected conversation ID survives tab reload in origin-scoped session storage; composer drafts and branch-operation state are held in memory, not persisted across reload.

Harness composer, model and history actions also wait for startup and the selected conversation's event subscription, history and model baseline. Enter during selection preserves the draft without admission or inference. Polling does not race a pending selection cursor; selection epochs prevent late creation from replacing a newer choice. This readiness guard changes no control placement. [Native Branch/Edit qualification](AUGMENTOR-HARNESS.md#native-branchedit-and-ordinary-sdk-inputs) additionally drives production Qt Window/Controller anchors, original-template Edit/Cancel, exact tool prefixes, saved-child reopening and active-turn refusal against the actual Pi owner with a synthetic provider.

### Native/Browser reasoning clients

Native reads `host.describe.capabilities.reasoning` and uses the four Pi methods above directly through its private IPC client. Standalone Browser receives the capability in initialize/connect and uses the extension message `reasoning` with a fixed action (`describe`, `configure`, `session`, `select`, `models`), `sourceSession` matching the selected conversation, and action-specific parameters. Unknown/prototype actions, wrong harness/phase, unselected or viewed chats and SDK workspace administration are refused before forwarding. Session IDs are constructed from the selected identity rather than caller-supplied parameters. The Pi Browser bridge additionally checks the target's Browser preset and refuses Linux chats. Global routes remain explicit profile administration, subject to Host revisions and all-chat idle guards.

Opening settings may create an unstarted blank conversation through the existing lifecycle; it does not submit a prompt. Browser refreshes current selection before capturing dialog identity. Working, controller/session/model or epoch changes invalidate dialogs and late responses. Open Native dialogs and the Browser form participate in existing maintenance admission. Harness and Browser share one independently authored DOM module; the local server exposes its fixed `/shared-reasoning/pi-reasoning.mjs` path without arbitrary extension-file access. [Qualification](AUGMENTOR-HARNESS.md#native-and-browser-reasoning-controls) includes actual received effort and role/scope tests; it does not qualify embedded workspaces or live providers.

Retained diagnostic search uses private hash-only payload derivatives and a persistent cursor key, with no stored query/body copy.
