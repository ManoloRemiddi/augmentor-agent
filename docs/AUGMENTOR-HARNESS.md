# Augmentor Harness — implementation and qualification

The owner authorized building the accepted [Pi migration](AUGMENTOR-HARNESS-MIGRATION.md) on 10 October 2026. The implementation branch is `feat/augmentor-harness`, based on canonical main `79784a5687b73234b9524e7a48e91f01306f73c9`. The older dirty checkout and historical private repositories remain intact. This is an incremental source candidate. Existing installed applications, selected releases, model settings, speech services and conversations have not been migrated.

## Available in this candidate

`apps/harness` is an authenticated local web interface named **Augmentor Harness**. It connects to the existing `packages/runtime` Pi owner. It does not run another agent loop. Chat renders provider-supplied reasoning and answers. The Trajectory view shows ordered request/tool/turn observations, recorded timings, indexed retained-metadata search and interval focus. Context shows the effective structured provider input after registered payload transformations, including system/messages/tool declarations and retained inline images. Parsed provider events are available in Trajectory when the provider exposes them through the supported SDK hook. Context displays the associated SDK usage against the model's declared capacity, API, thinking level and managed permission/tool-budget policy.

Context also exposes [recorded composition boundaries](#recorded-context-composition-boundaries): run preparation, aggregate message changes, converted SDK context, provider hooks and the managed memory return. Loaded resources are explicitly distinguished from observed consumption. Complete source attribution remains unavailable.

Standalone Pi Native and Browser can open a **read-only conversation inspector** in a browser. Native uses the three-dot menu → Trajectory & Context; Browser uses Settings → Models → Trajectory & Context. It opens Trajectory for the current conversation and provides the same Chat/Trajectory/Context presentation. [The scoped-inspection record](#native-and-browser-conversation-inspection) describes its separate authority, qualification and remaining inspection work.

The timeline projection is selected public DSH MIT source at `d743267388641bc76f17c45ce8b4c231aed1d32c`. The [source record and original license](../packages/harness-ui/vendor/dsh/SOURCE.md) identify its adaptations. Compiled distributions carry that notice under `dist/harness-ui/vendor/dsh`. The surrounding interface and product adapters are Augmentor-authored and retain `LicenseRef-Augmentor-MIT-Resale-1.0`; their license must not be described as unrestricted MIT. No DSH session/backend loop is copied.

The three root Pi packages are pinned to published **1.1.0**. Their SDK session owns execution, native history, cancellation, compaction and exact branching. The desktop specialist now composes the supported `finishTurn` hook. Browser sessions retain their restricted tool policy. Shared prompts, memory bindings and other product integrations retain their existing owners.

## Open and inspect

First build the source with `npm ci --ignore-scripts` and `npm run build`. Development must use an isolated, explicitly configured profile. Set `AUGMENTOR_PI_CONFIG`, `AUGMENTOR_PI_STATE`, `AUGMENTOR_SHARED_DATA` and `AUGMENTOR_SHARED_STATE` to separate development folders; use the existing model setup contract to configure that profile. Do not point development at the owner's installed state or change local model context, GPU placement or speech settings.

Run `npm start` with that environment. In a second terminal using the same profile, run `npm run harness`. It asks the already-running owner for `harness.open` and opens its private link in the default browser. `--session ID` opens an existing conversation. `--print-url` explicitly prints the private link for manual opening. No launcher command submits a prompt or starts a second runtime. An older owner without this method must be stopped through its normal lifecycle before a tested replacement can own that profile.

For a synthetic demonstration, `npm run harness:proof` starts a temporary profile, a deterministic loopback provider and the real Pi runtime. Its stdout identifies an ephemeral fixture URL. The fixture model reads `note.txt` through the actual Pi tool loop and clearly labels its answer as a test. Ctrl+C removes this fixture's temporary state. This proof does not use private prompts, production providers, microphones or installed application state.

The interface exposes available configured models; a missing selection does not silently choose a provider. New conversations require a working folder. Narrow windows expose conversation/history controls through **Conversations**. The existing Native and Browser layouts remain available; their standalone inspection entry points are qualified below. Embedded entry points remain required.

Harness Chat now places **Branch** beside Copy on persisted replies and **Edit** on the latest human input. Branch opens an exact native child without inference. Edit loads the original submitted words; Cancel restores the previous draft, and Send edit forks before that input and uses the ordinary durable queue. Earlier tool context remains, parents stay unchanged, and a steered correction retains earlier messages from its shared turn. Selected conversation identity survives tab reload; drafts remain in memory. Running/submitting actions are disabled. See [the Branch/Edit qualification below](#harness-branchedit-controls-and-steering-history) for failure boundaries and evidence.

**Prompt library** opens the existing shared editor without requiring an active conversation. It creates, renames, edits and deletes the same revisioned records used by Native and Browser. A saved `/name` inserts an editable draft on Enter, Tab or a completion click; a second Enter sends. Clipboard selection reads one snapshot. Shared improvement instructions are editable; Improve/Cancel/Undo uses one isolated, tool-free Pi draft request, qualified in the later prompt-improvement record. See [shared prompt qualification](#shared-prompt-library-and-editor).

## Observation and privacy contract

See [the observation store](../packages/observation/README.md) and [client protocol](PROTOCOL.md). Metadata capture is on during managed operation. Full request/tool/message diagnostic copies are **off by default**. **Save context history** enables future payload copies for that Pi profile. This switch neither reconstructs earlier requests nor deletes previously retained copies. Pi's ordinary native conversation history remains a separate private record.

Diagnostics live under `<Pi state>/observations` with mode-0700 directories and mode-0600 files. Retention defaults to 14 days and 512 MiB. Payloads expire before metadata under size pressure. Counters survive clear/expiry; a crash can leave a sequence gap but cannot reuse an acknowledged position. Incomplete journal tails and owned atomic-write leftovers are removed without executing work. A response reports missing, disabled, invalid, oversized or expired coverage honestly. Diagnostic clearing leaves native Pi history unchanged.

Known credential field names are redacted from retained structured bodies. Authorization headers are never observed by this adapter. Arbitrary user/tool content can contain secrets; the capture switch is not a guarantee of automatic content scrubbing. Payload chunks use UTF-8 byte cursors and complete characters. Large payload reads are bounded and do not reload the whole body for each chunk. Files cap at the smaller of 32 MiB and half the retention budget.

The request boundary is **provider payload after hooks**, verified against a synthetic provider's received object after two extension transformations. It is structured input, not a claim about exact HTTP bytes or every transport retry. Timings use monotonic differences within the producer process. SDK-normalized usage may contain zero defaults for unavailable provider fields; those fields are not independently verified measurements. Parsed provider events are captured after preceding stream hooks and before SDK normalization. Each managed request buffers at most 8 MiB of additional diagnostic event data; its `provider/stream` record reports observed/captured/dropped counts and complete, partial or disabled coverage. Bodies follow the same opt-in policy and known-field redaction rules as other captures. Custom adapters without request hooks report missing request correlation/timing; they never inherit the preceding request identity. This does not capture HTTP framing, headers or exact wire bytes. Exact context-source provenance, routed-policy explanation and separate retry-attempt capture remain gaps.

The context meter adds SDK input, cache-read and cache-write counts and compares that with declared model capacity. Output usage appears separately. A provider can omit usage fields and the SDK can normalize them to zero; the meter is therefore reported usage, not an independently tokenized count or capacity-enforcement guarantee.

Managed Pi settings explicitly disable install reporting, analytics and automatic cache warming. Cache warming is inference behavior rather than telemetry; disabling it prevents unsolicited warm-up inference in this managed profile. Model-network discovery is disabled. The runtime contract blocks external TCP attempts before imports and exercises configured loopback inference. This qualifies the pinned core in that synthetic environment; installed live services and separately approved extensions require their own destination inventory and network proof. European project roots do not establish data residence.

## Pi tool budgets and original evidence

The managed extension uses Pi 1.1.0's supported `turn_end` context-edit drafts, `SessionManager` projection and `refreshContext()` lifecycle. Before subsequent model requests, oversized text is reduced using an 8,192-code-point threshold, 4,096 head and 1,024 tail plus an original-entry recovery notice. Images, other non-text blocks and immutable original native entries remain. Binary-like text is withheld using the shared Augmentor evidence heuristic. Fresh `browser_snapshot`/`browser_tabs_list` text gets its first model step up to an aggregate 64,000-code-point allowance per boundary; binary evidence never qualifies. This is a per-result context budget, not a total-context cap or a display-journal limit.

The model's read-only `tool_result_excerpt` resolves original entry IDs only on the current conversation branch, with bounded 2,048-code-point excerpts and literal case-insensitive search. It cannot retrieve sibling/future entries or reintroduce binary-like text. **Trim saved tool context** applies the deterministic repair while idle, including after an owner restart without creating an SDK session or contacting a provider. Loaded owners refresh their context through the public SDK API. Originals are preserved; no tool is rerun. Existing oversized results are also repaired before loading the SDK owner. Current-format native history is qualified; old-format migration/backup and large-history costs still require cutover qualification. See [the context-budget contract](CONTEXT-BUDGET.md#pi-harness-port--october-10-candidate).

The follow-up below ports DSH's repeated/error/progress advisory checkpoints. The follow-up below also ports an action ledger and bounded response recovery. Live-provider and installed qualification remain migration gates under [task reliability](TASK-RELIABILITY.md).

## Transport and ownership

The HTTP server listens on `127.0.0.1`, with an ephemeral port and a random bearer token. Its private descriptor is `<Pi state>/harness.json`. The browser receives the token in a URL fragment, stores it only in that tab's session storage and removes the fragment from visible history. Never publish this descriptor or a real profile's link.

API requests require the bearer token and the expected Host and browser Origin. Static paths are fixed. CSP permits local scripts/styles and retained data images, forbids external connections and framing, and responses disable caching/referrers. This is a trusted local operator interface for its Pi profile. Its RPC allowlist excludes direct model configuration and shutdown. Browser/embedded scoped bridges do not receive this operator token.

A browser watch is tied to its conversation and client identity. Approvals/questions must match that watch. Concurrent `harness.open` calls reuse one server. The runtime binds its owned IPC socket before opening journals, so simultaneous fresh launches cannot both recover a profile. Ordinary IPC disconnect does not cancel a pending approval while a Harness watch still owns that conversation.

The live ring caps at 4,096 frames and 16 MiB, and each response stays within the 1 MiB transport limit. Loss is identified for the affected conversation; clients refresh durable history and recent observations without replaying actions. Stable display sequences suppress overlap between snapshots and live frames. The chat projection retains partial text and reasoning after Stop/restart, reports missing tool outcomes honestly, and periodically reconciles active status. Idle runtime shutdown has its own observation rather than impersonating a user Stop. The ledger renders a bounded visible row range, preserves visible button identities while scrolling and pairs tools by request/tool identity. Metadata pages use a derived byte-offset index. The search field scans retained metadata beyond the initial page and states that payload bodies are excluded. Native history indexing, payload/full-history search, owner-restart connection discovery and longer performance qualification remain required. Display paging has its own qualification below. See [indexed metadata qualification](#indexed-trajectory-metadata-and-search).

## Durable prompt queue — October 10 source candidate

The product owns waiting inputs in a private, durable queue, and the same Pi `AgentSession.prompt` owns each admitted turn. No parallel agent loop or second SDK session is introduced. Text, stable request ID and fingerprint are persisted before dispatch. Each waiting prompt is admitted once in FIFO order; removal acts on its existing ID. Completed receipts retain their ID/fingerprint while discarding prompt text. A duplicate RPC with the same input returns its receipt; changing the input under the same ID fails. The queue bounds 100 waiting/visible rows and 512 KiB of serialized waiting/visible state. IDs are not recycled after that bound or after completion.

Native and Browser reuse their established queue row above the composer, with immediate clearing, ordered rapid submission, failure-text retention and delivered-user-message correlation. Pi's capability is negotiated from the host. The local Harness uses the same product semantics and a presentation module adapted from Augmentor's public Browser queue. Stop synchronously persists pause before awaiting helpers or aborting the current SDK turn. Ordinary waiting prompts resume automatically only after a successful preceding turn. Error, bounded-recovery exhaustion, Stop and cold restart leave waiting work paused. An explicit idle Send resumes older waiting inputs before the new input; the Harness also provides Continue queued prompts. Reconnect alone cannot resume work. Native/Browser/Harness ignore older queue revisions and scope frames to their selected conversation.

A process death during dispatch/execution converts that receipt to unknown; the original input is never automatically repeated. The receipt remains visible even when its user-message delivery had been confirmed. Remove and Steer are unavailable. **Keep interrupted** explicitly acknowledges the receipt without retrying it, verifying an external outcome or resuming waiting work; its honest notice is saved. The owner must inspect and resolve uncertain external actions before continuing. This acknowledgment is not semantic action reconciliation or proof of success. Legacy protocol calls without queue mode retain busy rejection; explicit queue mode supports concurrent admission, not concurrent execution.

This historical queue-only slice advertised **queue true, steering false**. Selective removal and stable IDs are absent from the pinned SDK's public string queue, so that queue is not used as the product ledger. The responsive steering follow-up below supplies generation supersession and active tool boundaries. The combined queue/steering P0 gate remains open. Windows file writes synchronize the file and use atomic replace; POSIX also synchronizes the parent directory and checks private ownership/modes. Windows profile ACL and physical platform acceptance remain part of release qualification.
